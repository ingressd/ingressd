# Node agent (managed mode): behaviour and decisions

How the node implements its side of [ARCHITECTURE.md](ARCHITECTURE.md) §4–§8. The panel implements the other side from `pkg/nodeproto`; this page lists the behaviour it can rely on and the choices made where the contract left room.

## Files

| Path | Content |
|---|---|
| `<state-dir>/node.json` (0600) | node id, credential, pinned org signing key, panel URL, hostname, public IPs, SSH port, applied revision and hashes. Its presence means "managed". |
| `<state-dir>/edge-endpoint.json` | hostname / public IP that sites and connectors use. **Kept after detach** so connector endpoints keep working on a node that became standalone. |
| `<state-dir>/node-usage.json` (0600) | usage seq, WireGuard counter baselines, unacknowledged usage messages |
| `<state-dir>/node-runtime.json` | connection state for `ingressd node status` |
| `<state-dir>/node-snapshot.yaml` | last applied snapshot config (restored at startup if `config.yaml` was edited locally) |
| secret `wg-mesh-node` | the node's WireGuard mesh private key (public key sent in `hello.mesh_public_key`) |

## Protocol behaviour

- **Connect**: `GET /api/node/v1/connect` with `Authorization: Bearer <node_id>.<credential>`; `hello` first; jittered exponential backoff 1 s → 60 s (reset after a connection that lasted 30 s); WebSocket pings every 30 s; app-level `ping` → `pong` with the same envelope id.
- **Replies echo the request envelope `id`**: `applied`, `diag_result`, `connector_token`, `site_config`, `smartdns_recent`, `pong`, and `discovery` (the `discover_request` id; a failure is an `event{kind:"discovery_failed"}` with that id).
- **Snapshots** are applied one at a time, in arrival order. Rejected: bad, legacy v1, expired or other-node signature (see Trust model); `revision <= applied` unless `force` (an identical redelivery of the applied revision, same config and secrets, is answered `ok` without re-applying); invalid config (error lists YAML paths); secrets named `wg-mesh-node` or `wg-*-edge` / `wg-*-site` (node-generated); **a config whose `edge.ssh_port` differs from the node's sshd port** while the managed firewall is on (lockout guard; the port comes from enrolment). On apply failure the previous config and secrets are restored and the apply engine rolls the system back.
- **Status** is sent at connect, every 15 s, and immediately when health, checks, tunnel up/transport, certificate states, applied revision, exits or mesh peers change (checked every 5 s). `health`: `down` if the edge proxy is unreachable or the config is invalid, `degraded` on any other failed check (warnings included), else `ok`. Certificates: one entry per app host, redirect source and access portal host: `valid`; `failed` with Caddy's tls log error when issuance failed and there is no valid cert; otherwise `issuing`. `uptime_seconds` is the agent process uptime.
- **Usage** (additive `usage_ack`): every 60 s the node records a delta (apps from the access log, mapped host → app key including wildcards and redirect sources; sites from WireGuard counters, baseline at first sight; exit routing from the hook) with `seq = previous + 1`, persists it, and sends it. Empty intervals produce no message. Messages stay pending until the panel sends `usage_ack{seq}` (acknowledges every seq ≤ it) and are all resent after every reconnect, so the panel must dedup by seq. Without acks the queue is capped at 7 days of messages. The interval at shutdown is recorded too.
- **Live preview**: `live_subscribe` streams matching entries (hosts and/or apps; empty = all) as `log` batches every 0.5 s, at most `max_per_second` (default 20, max 200) entries per second, `dropped` counts the rest. Query values are removed (`/a?token=&x=`). Subscriptions end at `until` (max 1 h), on `live_unsubscribe`, or when the connection drops (the panel re-subscribes).
- **Diagnostics** (`diag_request.timeout` in nanoseconds, default 10 s): `origin` → steps `edge`, `tunnel`, `connect`, `tls` (https origins), `http`; codes `tunnel_down` (interface down or no handshake within 180 s), `no_reply` (connect timeout or ICMP unreachable while the tunnel is up), `refused` (RST), `tls_error`, `timeout` (connected, no HTTP response), `http_error` (5xx), `ok`; `error` for unknown apps. `http` → `https://<host>/` dialled at the node's public IPv4:443 with SNI, verified against system roots plus Caddy's internal CA; ok for 2xx/3xx/401/403. `tunnel` → `host` is the site name (or `app` selects its site).
- **connector_token_request** → join string = base64url (unpadded) JSON `{"u","t","ca"}` (`internal/connector/proto.Join`, `EncodeJoin`). `u` is `https://<hostname>` when the node enrolled with one, else `https://<public-ip>` with `ca` = Caddy's internal root, which issues the bare-IP certificate. The `/.ingressd/` connector endpoints are served on that host in both cases.
- **site_config_request** → `tunnel.SiteConfig` with the node's hostname/IP as endpoint (`wg-quick` includes the `DNS =` line for UniFi).
- **discover_request** → `connector.Server.RequestDiscovery` (from the connector+CI stream, `internal/connector/discovery.go`): the request is stored in connector.json and delivered as `TunnelConfig.discover_id` on the connector's next poll (only to connectors that send the `discover` poll parameter); the connector POSTs `proto.DiscoveryReport` to `/.ingressd/connector/discovery` and the node forwards it as `discovery` (echoing the request id). Failures (unknown site, no connector, `ErrDiscoveryUnsupported`) come back as `event{kind:"discovery_failed"}` with the request id; a report with `error` set also produces that event (without id) before the `discovery`.
- **detach** (message or `ingressd node detach`): node.json, runtime and snapshot files are deleted; config, secrets and edge-endpoint.json stay; an `event{kind:"detached"}` is sent if connected; serve then follows `config.yaml` again.

## Trust model (panel → node)

The node trusts two things it pinned at enrolment: the panel's **TLS identity** (system roots) and the org's **ed25519 signing key** (`node.json` `org_signing_key`).

- **Transport: https/wss only.** `node enroll --panel`, the `panel_url` an enrol response returns and the URL in `node.json` must be `https://` (the control channel is `wss://`). The enrol response may move the node to another host but never to `http://`; the enrolment client refuses redirects away from https. `INGRESSD_INSECURE_PANEL=1` allows plain http for the fake panel in tests only and is logged as an error on every enrolment and connect. A node enrolled over http on an older release refuses to connect after the update (re-enrol with https). The enrolment token is read from `--token-file FILE|-` or `INGRESSD_ENROLL_TOKEN` (`--token` still works but puts it in argv); the installer pipes it on stdin.
- **Snapshots: v2 signatures only** (`nodeproto.SignV2` / `VerifyV2`, domain `ingressd-snapshot-v2`). The signature covers node ID, org ID, revision, force, `issued_at`/`expires_at` (10 min, signed at delivery time by the panel), the config hash, secrets and removals. The node rejects a snapshot that is v1 (`homeedge-snapshot-v1`, replayable anywhere, any time), for another node or org, expired or issued in the future (±2 min clock skew), valid for more than 15 min, or a forced snapshot it already applied (replay cache until expiry). Validity is checked at arrival, not after queueing. The node needs a roughly correct clock (NTP).
- **Signed requests** (`Envelope.auth`, `nodeproto.EncodeSigned` / `VerifyAuth`, domain `ingressd-request-v1`): ed25519 by the org key over type, envelope id, node ID, org ID, a random nonce, `issued_at`/`expires_at` (2 min) and the SHA-256 of the data bytes. The node rejects unsigned, mismatched, expired and replayed (nonce cache) messages of these types and answers with an error (`connector_token`, `site_config`, `diag_result`) plus `event{kind:"request_rejected"}`:

  | Type | Why signed |
  |---|---|
  | `connector_token_request` | mints a connector enrolment token (re-enrolment replaces the site's WireGuard key) |
  | `site_config_request` | returns the site's WireGuard private key |
  | `detach` | leaves managed mode |
  | `l4_allow` | opens an L4 service to an IP |
  | `auth_revoke` | revokes sessions (state change) |
  | `upgrade_request`, `connector_update` | installs software (`force` allows a signed downgrade); the manifest is release-signed too |
  | `discover_request`, `smartdns_recent_request`, `live_subscribe`, `diag_request` | reveal LAN services, DNS lookups, access logs; trigger probes |

- **Not signed** (TLS trust only): replies to node-initiated requests, `auth_otp_start_result`, `auth_otp_verify_result` (decides a sign-in) and `storage_response` (shared certificate storage); they are correlated with random node-chosen envelope ids, so only the authenticated panel connection can answer. Signing them would need the panel to sign per-response with the org key on the OTP and storage paths (a redesign of `hostedauth`/storage, not done). Also unsigned: `ping`, `usage_ack`, `live_unsubscribe`.
- **Negotiation.** The agent lists `snapshot-v2` and `signed-requests` in `hello.capabilities`; the panel signs v2 / signs requests only for nodes that list them and keeps the v1 / unsigned formats for older agents. The agent never accepts the old formats. Deploy the panel before updating nodes: an updated node behind an old panel rejects every snapshot and signed-type request until the panel is updated.

## nodeproto changes (additive)

- `TypeUsageAck` / `UsageAck{seq}` (panel → node).
- `TypeStorageRequest` / `TypeStorageResponse` (`storage_request` node → panel, `storage_response` panel → node echoing the id): shared certificate storage, see [CERT-STORAGE.md](CERT-STORAGE.md). The first node-initiated request/response pair; the agent correlates replies by envelope id (`internal/nodeagent/storage.go`).
- `EnrollRequest.SSHPort`, `Hello.SSHPort` (`ssh_port`, omitted when unknown = 22). The compiler should set `edge.ssh_port` to it; the node refuses snapshots that would close it.

## Hosted Access (email provider `panel`)

Managed nodes get `email: { provider: panel }`: the access portal (and login-to-play) never holds SES/SMTP credentials. Codes are emailed by the panel from one address with one branded template, so sign-in works on whichever node of the org a user lands on.

- **Codes.** `POST step=email` still applies the node's own rate limits and cooldown (`access.otp`), then sends `auth_otp_start{email, policy, label, client_ip, host, ttl, length, attempts}` in the background (response timing is the same whether or not a code is sent). `step=code` sends `auth_otp_verify{email, code}`; wrong codes also count against the node's local lockout. Each request carries an envelope id; the panel answers `auth_otp_start_result` / `auth_otp_verify_result` with the same id (`pkg/nodeproto/auth.go`). Without a panel connection the portal answers 503 "temporarily unavailable" (no local fallback). Node-local SQLite OTP storage stays for `ses`/`smtp`/`log`.
- **Keys.** `access.session_key` / `access.jwt_key` are `secret://` references to org-wide keys the panel generates and delivers in the snapshot, age-encrypted to this node (`org_access_session_key`, `org_access_jwt_key`). With them set the node generates no keys of its own. Without them (standalone) the node keeps generating `access_session_key` / `access_jwt_key`.
- **Sessions on any node.** Callback codes are sealed (PASETO v4.local under a key derived from the session key) instead of stored, so the app callback may land on another node than the portal; each node redeems a code once. Portal and login-to-play cookies are self-contained: a node that never saw the session imports it on first use. App cookies are validated offline by edge_auth everywhere.
- **External portal (`access.portal_url`).** With the panel's central portal the node serves no portal host: `edge_auth` redirects to `<portal_url>/login?app=&rd=` (sign-out: `<portal_url>/logout`) and redeems the sealed code the panel issues at `/.ingressd/callback`. At every code exchange the node evaluates the app's policies for the code's email and the visitor's IP (sent by `edge_auth`) and grants only what they allow (403 "not allowed" otherwise), whoever sealed the code. `portal_url` needs org-wide keys and excludes `portal_host`; `login_to_play.portal_host` may then be empty (players sign in on the panel). Relayed `l4_allow` entries are applied only for login-to-play services whose policy allows the entry's email and address. Shared formats (keys, tokens, policy engine) are in `pkg/access`.
- **Revocation.** Signing out on a node revokes locally and reports `auth_revoke{sid, email, expires}`; the panel stores it and relays it to the org's other connected nodes (applied as a revoked session row, so edge_auth's revocation list includes it within seconds). Snapshots also carry `access.revoked_sessions` (for nodes that were offline) and `access.revoked_before` (per email or `"*"`; "sign everyone out" in the panel). edge_auth rejects app cookies issued before a `revoked_before` cut-off (the revocation list gained a `before` map).
- **Login-to-play.** `/join/<service>` on a play host uses the same email-code flow (`auth.Service.PlayAuthenticate`): signed-in players get a `__edge_play` cookie on the play host; the service's policy is checked for the verified email and the player's IP. Each allowlist entry a player adds is reported as `l4_allow{service, ip, email, expires}`; the panel relays it to the org's other nodes that have that L4 service in their config, which add it to their local allowlist store (no re-report). Standalone nodes use their local email provider for login-to-play.
- **Identity providers and header tokens** ([ACCESS-PROVIDERS.md](../ACCESS-PROVIDERS.md)). The agent lists `access-identity` in `hello.capabilities` (`nodeproto.CapabilityAccessIdentity`): it loads configs with `apps.<app>.login_methods`, the identity-provider and `login_method` selectors, `access.providers` and `service_tokens.<name>.header`, and redeems callback codes that carry a login method and sign-in facts (claims `m`, `attrs`) or a user that is not an email (`steam:<id>`). `config.Config.IdentityFeatures()` lists what in a config needs it; the panel must not send such a config to a node without the capability (older agents fail to load it). On the central portal the panel runs the provider sign-ins (its own per-org provider settings; nodes need no provider secrets) and seals the facts into the code; the node keeps only the facts its own policies refer to and evaluates them at the exchange. Header-token secrets reach nodes as ordinary snapshot secrets (age-encrypted to each node).
- **Limits.** Rate limits apply on the node (per email, per IP, lockouts) and on the panel (per email, per client IP across orgs, per org per UTC day: `--access-email-daily-cap`, default 500).

## Decisions

- **Local admin UI/API removed** (`internal/api`, `internal/admin`, `internal/ui`, `web/`). The `admins:` config section is still parsed and validated so older configs load, but nothing on the node uses it. `edge.admin.hostname` now only names the host for machine endpoints (`/.ingressd/`) and the default site endpoint; its root path answers with a short text.
- **Managed mode ignores local edits**: the serve loop no longer applies `config.yaml` changes while node.json exists (warning logged once per distinct content); at startup the last snapshot's config is restored if the file was edited.
- **`ingressd import`** refuses on a managed node (detach first).
- **Enrolment** creates the config dir, git repo, age identity and a minimal `version: 1` config if missing. Public IPv4 is detected from the route to the panel only when it is a public address; otherwise pass `--public-ip`.
- **Test-only env overrides** for the netns test: `INGRESSD_AGENT_USAGE_INTERVAL`, `INGRESSD_AGENT_STATUS_INTERVAL`, `INGRESSD_INSECURE_PANEL` (plain-http fake panel). `INGRESSD_IDP_TEST_BASE` (fake identity providers) only exists in binaries built with `-tags idptest` (`bin/ingressd-idptest`, access-idp suite); release builds cannot redirect provider endpoints.
- **Installer** (`deploy/install-node.sh`): POSIX sh; downloads `ingressd-linux-<arch>` and `ingressd-edge-linux-<arch>` plus `SHA256SUMS` from `<panel>/downloads/` (or `--artifacts`), or installs from `--bin-dir`; embeds the systemd units; detects sshd's port and passes `--ssh-port`; arms `ingressd-firewall-guard` (`systemd-run --on-active=5min nft delete table inet ingressd`) and stops it once `ingressd node status` reports a connection. Re-running upgrades and keeps the enrolment.

## Multi-PoP sites (one site, several nodes)

The panel can attach a site to several nodes. Node side:

- **Config**: each node gets the site's tunnel with its own `/30` transit (from `100.64.0.0/10`, edge `.1`, site `.2`) and listen port, plus `tunnels.<t>.siblings` — the site's attachments on other nodes: `{node, endpoint, edge_public_key, transit, ws_url}` (`config.TunnelSibling`). Sibling transits must not overlap this node's transits. A node never configures siblings itself; it hands them to the connector. Router sites import one WireGuard config per node (`AllowedIPs` = that node's `/30`).
- **Status**: `TunnelStatus.edge_public_key` is this node's WireGuard key for the tunnel (the panel lists it as a sibling on the other nodes); `connector_public_key` is the connector's key — the one that enrolled here, else the configured `public_key`.
- **Connector accepted without enrolment**: `tunnels.<t>.public_key` is authoritative for the WireGuard peer (it always was for rendering). A connector that enrolled on another node is accepted on the connector endpoints by:
  - **the tunnel**: plain HTTP on `<edge transit address>:51819` (`proto.TunnelControlPort`), serving `GET /.ingressd/connector/poll`, `POST /.ingressd/connector/report`, `POST /.ingressd/connector/discovery`. A request is answered only when it comes from a connector tunnel's site address to that tunnel's edge address; WireGuard guarantees only the site's peer can use that source, and the managed firewall admits the port only on the tunnel interface (`iifname he-<t> ip saddr <site> ip daddr <edge> tcp dport 51819`). `ingressd serve` listens on `0.0.0.0:51819`.
  - **a `IngressdKey` header** on the public endpoints (poll, report, discovery, the WebSocket bridge): `IngressdKey <tunnel>.<unix>.<hex HMAC-SHA256>` keyed with X25519(site private, edge public) = X25519(edge private, site public), ±5 min (`proto.KeyAuth` / `CheckKeyAuth`).
  - Reports from such a connector create its entry in `connector.json` (health, transport, discovery work as for an enrolled one).
- **Tunnel config** (`proto.TunnelConfig`) carries `siblings: [{node, endpoint, edge_public_key, address (site .2/30), edge_address, ws_url}]`; the revision covers them, so a sibling change wakes the connector's long poll.
- **WebSocket bridge**: `/.ingressd/tunnel/<tunnel>` as before, and `/.ingressd/connector/ws` with the tunnel taken from the authorization header.
- **Connector**: one WireGuard device, one peer per edge (`AllowedIPs` = the edge's `/30`), one transit address per edge on the device. Each edge has its own transport (UDP, WebSocket fallback), long poll (over the tunnel when it is up, else the public URL with the credential or a `IngressdKey` header) and health reports. The edge list is reconciled every 60 s and on any tunnel loss: siblings any edge lists are added; an edge is dropped when it answers 410, or when no edge polled in the last 2 min lists it and it has not answered for 3 min; the last edge is never dropped. Old single-edge state files migrate on load. Transparent L4 replies (TUN mode) leave through the first edge that is up (WireGuard routes by destination, so one edge at a time owns `0.0.0.0/0`). Join strings may list several edges (`{"e":[{"u","ca"}],"t"}`); enrolment tries them in order.
